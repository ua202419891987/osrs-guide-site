You followed the setup steps. The server says it's running. But your friends see "Connection timed out," the world never spawns, or the whole thing crashes on launch. 📋 1. Read the Logs First — Where Every Fix Starts

Before you touch a single setting, open the server log. Windrose writes a live log file every time the dedicated server starts, and it is brutally honest about what went wrong. Players who skip this step spend hours "trying things" when the answer was on line 14 the whole time. The log is the difference between guessing and diagnosing.

The server log is created next to your WindroseServer.exe (or start_server.sh on Linux) in a folder usually named Logs/. On Windows the default path is %USERPROFILE%\AppData\Local\Windrose\Saved\Logs\WindroseServer.log. If you launched the server from a terminal, the same text is printed live — scroll up before you Ctrl+C out of it.

🔍 How to Read a Windrose Server Log in 60 Seconds

1. Open the log file in any text editor (Notepad++, VS Code, or even plain Notepad).

2. Search (Ctrl+F) for the words Error, Failed, Exception, and refused. These four terms cover roughly 80% of real failures.

3. Read the FIRST error, not the last. Windrose often throws a cascade of secondary errors after the initial fault — fixing the root cause clears the rest.

4. Note the timestamp and the line that mentions bind, port, config, or version. That single line tells you which section of this guide to jump to.

Log Reading Pro Tip: A server that prints Listening on 0.0.0.0:3478 is correctly bound and reachable on your local network. If you see bind: address already in use, something else (often a second server instance or a stuck process) is holding port 3478 — kill it before continuing. If you see bind: permission denied, you are likely running without admin/root rights.

If your log shows a clean Server started line but players still cannot join, your problem is NOT in the server — it is in the network path between players and your machine. Jump straight to Section 2 (port forwarding). If the log shows a config parse error, jump to Section 6. Matching the log message to the section saves you the most time.

🌐 2. Players Can't Connect — Port Forwarding (Port 3478)

This is the #1 cause of "the server is up but my friends can't join." Windrose's dedicated server uses port 3478 on both UDP and TCP. The game's query, handshake, and gameplay traffic all ride this single port pair. If even one protocol is blocked, the server appears online in your own client (because you connect over localhost) but is a black hole to the outside world.

The Most Common Mistake: Router port-forwarding screens let you pick "UDP," "TCP," or "Both." Players who select only UDP (or only TCP) report that the server shows up in the browser list but connections drop instantly, or never complete. You MUST forward 3478 for BOTH protocols, or use the "Both"/"TCP+UDP" option if your router offers it.
1

Find Your Server Machine's Local IP

On the host machine, open a command prompt and run ipconfig (Windows) or ip addr (Linux). Look for the IPv4 address on your active adapter — typically 192.168.x.x or 10.x.x.x. This is the internal address your router sends forwarded traffic to. Write it down; you need it in step 3.

2

Log Into Your Router

Open a browser and go to your gateway address — most commonly 192.168.1.1 or 192.168.0.1. The username/password is usually printed on the router sticker (often admin/admin). If you changed it and forgot, you may need a router reset.

3

Create the Port Forward Rule

Find "Port Forwarding" (sometimes "NAT" or "Virtual Server"). Create a rule: External Port 3478, Internal Port 3478, Protocol BOTH (UDP+TCP), Internal IP = the address from step 1. Save and reboot the router if prompted. Create TWO rules if your router has no "Both" option — one UDP, one TCP.

4

Confirm Your Public IP

Search "what is my IP" on the host machine. That public address is what friends paste into their join field. If your ISP uses CG-NAT (common on mobile and some fiber plans), port forwarding will NOT work — see the note below.

Stuck Behind CG-NAT? If port forwarding does nothing no matter what you try, your ISP may be using Carrier-Grade NAT, which hides you behind a shared public IP you cannot forward through. Confirm by comparing the IP your router reports as "WAN" vs the IP "what is my IP" shows — if they differ, you are on CG-NAT. Options: ask your ISP for a static public IP (sometimes a paid add-on), or use a VPN/ tunneling service that supports UDP game traffic.

After forwarding, have a friend try to connect using your public IP followed by the port: 123.45.67.89:3478. If it works, the network path is open. If it still fails, the block is almost certainly the firewall (Section 3) or the PublicIP config field (Section 6) — not the router.

🛡️ 3. Firewall & Antivirus Blocking the Server

Even with perfect port forwarding, Windows Defender, your third-party antivirus, or a cloud firewall can silently drop inbound traffic to port 3478. The server "runs" because nothing on your machine is stopping it — but the firewall stops everyone else before they reach it. This is maddening because the log shows no error; the packets simply never arrive.

🪟 Allow the Server Through Windows Defender Firewall

1. Open "Windows Defender Firewall" → "Advanced settings" → "Inbound Rules" → "New Rule."

2. Rule type: Port. Protocol: TCP, Specific ports: 3478. Action: Allow the connection. Profile: check all three (Domain, Private, Public). Name it "Windrose Server TCP."

3. Repeat the same steps for UDP port 3478 and name it "Windrose Server UDP." You now have two inbound rules.

4. Also add the server executable (WindroseServer.exe) as an allowed app under "Allow an app through firewall" so outbound handshakes are never blocked either.

Antivirus Quiet-Kill: Several third-party antivirus suites (notably those with "behavioral network protection") flag game server executables as suspicious and block their sockets without a visible popup. If Windows Defender rules are correct but players still can't connect, temporarily disable your antivirus and retest. If it works, add WindroseServer.exe to the antivirus allowlist rather than leaving protection off.

Linux hosts need the equivalent: sudo ufw allow 3478/tcp and sudo ufw allow 3478/udp, then sudo ufw reload. Cloud providers (AWS, GCP, Azure) additionally require their security group / network ACL to permit inbound 3478 UDP+TCP — the OS firewall is only half the story there.

✓

Quick Firewall Self-Test

From a second device on the SAME local network, try connecting using the host's local IP (192.168.x.x:3478). If that works but the public IP does not, the firewall is fine and the problem is port forwarding or CG-NAT. If even the local connection fails, the firewall or the server bind is the culprit — go back to Section 1 and re-read the log.

🗺️ 4. World Won't Generate / Stuck on Loading Screen

A server that launches, binds the port, and then either never spawns a world or leaves players frozen on "Loading..." is almost always choking on a configuration or save issue — not the network. The host sees the server "running" because the process is alive, but the world thread crashed or is waiting on bad input.

The most frequent causes, in order of likelihood:

1. Corrupted or partially-written save. If the previous session was force-closed (power loss, crash, kill -9), the world save can be left in a half-written state. Windrose then hangs trying to load it. Fix: rename or move the SavedArks/SaveGames folder for that world, let the server generate a fresh one, then migrate your structures back manually if needed.

2. Illegal characters in ServerName or WorldName. Emojis, non-ASCII symbols, and some punctuation cause the world generator to abort silently. Use plain ASCII letters, numbers, and dashes only.

3. MaxPlayers set to 0 or a negative number. The server interprets 0 as "no slots" and some builds then fail to spin up the world thread. Set it to at least 1 (typically 4–10 for co-op).

4. Wrong WorldSeed format. If you supply a seed, it must be a valid integer or the exact string the game expects — a blank or malformed seed can loop the generator. Leave it auto if unsure.

"Stuck at 99% Loading" Is a Client-Side Tell: When a joining player freezes at the loading bar while the host is fine, the client and server are disagreeing on world data — usually a mod mismatch (Section 7) or a version difference. It is NOT a port problem. If the host ALSO sees no world, it is a server config/save problem (above).
Force a Clean World Test: To isolate whether the save is the problem, temporarily point the server at a brand-new, empty save directory (change the SaveDir or world name in the config). If the new world generates instantly, your old save was the culprit. You can then attempt to recover structures by copying the Players and Structures subfolders from the old save into the new one — though this is not always clean, so back up first.

💥 5. Launch Crash on the Host Machine

If the server process closes immediately (or within a few seconds) every time you launch it, you are dealing with a host-side crash — not a networking problem. The log (Section 1) is essential here, but the failure patterns are predictable enough to triage directly.

🔧 The Launch-Crash Checklist (Run Top to Bottom)

1. Run as administrator / root. Binding to a port and writing to protected save directories fails without elevated rights on some systems. Right-click the launcher → "Run as administrator" on Windows, or prefix with sudo on Linux.

2. Verify the game files. A corrupted core file causes an instant crash with an "missing module" or "null reference" exception. On Steam, right-click Windrose → Properties → Installed Files → "Verify integrity of game files." Dedicated server tools have their own verify step.

3. Check RAM. Windrose dedicated servers want at least 4 GB free; world generation spikes higher. A crash with an OutOfMemory line means you need to close other apps or assign more to the server.

4. Remove recently added mods. A mod that failed to download or is built for a different version will crash the host at load. Move your Mods folder aside and relaunch (see Section 7).

5. Java / runtime mismatch (Linux). Some server wrappers depend on a specific runtime. An UnsupportedClassVersion error means your runtime is too old — update it.

Do Not "Just Reinstall" First: A full reinstall fixes maybe 10% of launch crashes and costs you an hour plus a re-download. Read the log, run the checklist above, and only reinstall if the error explicitly names a missing or corrupt game asset after verification failed to replace it.

If the server crashes only when a specific friend joins (but runs fine solo), the crash is actually a client-mod or version conflict triggering a server-side exception during sync — that is Section 7 territory, not a pure host crash.

The PublicIP Trap: The official docs are genuinely contradictory here — one page says "always set PublicIP to your router's WAN address," another says "leave it blank for auto-detection," a third example hardcodes a LAN IP. The authoritative answer: leave PublicIP blank unless auto-detection fails, in which case use your true public IPv4 (not the 192.168.x.x LAN address). After editing the config, always restart the server cleanly — do not rely on a hot-reload that may not re-read every field. Watch the log for a clean Server started line and confirm the port bind message matches your settings.

🔄 7. Version & Mod Conflicts

The final category of "something is wrong" is mismatch: the host and clients are not speaking the same language. Windrose is strict about version parity, and mods multiply the failure surface. Symptoms range from launch crashes to the "stuck at 99% loading" freeze from Section 4.

🧩 Diagnosing a Version Conflict

1. Compare build numbers. The host's server log prints a version string at startup (e.g., Windrose Dedicated Server v0.7.2). Every joining client must be on the same version. Steam usually auto-updates clients, but a player who paused updates, or is on a beta branch, will mismatch.

2. Check the beta branch. If the host opted into a beta/preview build, only clients on the same beta can join. Either everyone opts in, or the host returns to stable.

3. Confirm mod parity. Every mod the server loads MUST be installed and enabled on every client, in the same load order. A missing mod causes the client to either crash on join or hang at loading while it waits for data the server expects to send.

4. Watch the log for mismatch lines. Look for version mismatch, mod checksum failed, or client outdated. These name the exact offender.

Mod Load Order Matters: Unlike some games, Windrose applies mods in the order listed in the config. If the server loads "Mod A then Mod B" but a client loads "Mod B then Mod A," even identical mod sets can produce different world data and a sync failure. Standardize the load order across host and all clients — ideally by sharing the server's mod list file directly.
Clean-Mod Test: If you suspect mods, move the server's Mods folder aside, disable all client mods, and relaunch. If everything works vanilla, re-add mods ONE at a time, restarting the server between each, until the culprit reveals itself. This is slower than guessing but it is definitive.

Version conflicts are the easiest class of problem to prevent and the most annoying to live with. The single best habit: before inviting friends, confirm everyone right-clicked Windrose → "Properties" → made sure "Receive beta updates" matches the host, and that Steam finished downloading the latest patch. A 30-second version check prevents 90% of "we can't join" nights.

❓ FAQ — Server Troubleshooting Questions

Q: The server shows "online" in my own client but friends get "Connection timed out." What's wrong?

This is almost always port forwarding or firewall, not the server itself. Your client connects over localhost (which never touches the router), so you see it fine. Your friends hit your public IP, which is blocked. Re-check Section 2 (forward 3478 UDP+TCP) and Section 3 (firewall allow rules). Also confirm you are not behind CG-NAT.

Q: Do I really need both UDP and TCP on port 3478?

Yes. Windrose uses UDP for the bulk of real-time gameplay traffic and TCP for the initial handshake/query. Opening only one makes the server appear alive but unreachable or unstable for joiners. If your router has a "Both" or "TCP+UDP" option, use it; otherwise make two separate rules.

Q: Should I set PublicIP in the config?

Leave it blank for auto-detection in the vast majority of cases. Only set it to your true public IPv4 if auto-detection fails (some ISPs/setups need it). Never set it to a 192.168.x.x LAN address — that is the most common reason a correctly forwarded server stays invisible to the internet.

Q: My friends freeze at 99% loading but I (the host) am fine. Is this a port issue?

No. A host-side world that loads fine means networking and config are okay. A client freezing at the loading bar is a version or mod mismatch — the client and server disagree on world data. See Section 7: compare build numbers and mod loadouts.

Q: The server crashes the instant a specific player joins. Why?

That points to a client-side mod or version conflict triggering a server exception during sync. Have that player disable all mods and verify their game files, then rejoin. If it works, a mod or outdated client was the cause. Re-add their mods one at a time to find the offender.

Q: Can I run multiple Windrose servers on one machine?

Yes, but each needs a unique Port (and matching forward), a unique QueryPort, and ideally its own save directory. Two servers sharing port 3478 will conflict with a bind: address already in use error in the log. Increment ports (3478, 3479, ...) and forward each.

Q: The official wiki says X but the in-game tooltip says Y. Which do I trust?

This guide's fix order is the authoritative one: logs first, then port (UDP+TCP), then firewall, then config fields (especially PublicIP and MaxPlayers), then version/mod. The official sources genuinely contradict each other on PublicIP and on whether TCP is required, so when they disagree, follow the order and values given here — they reflect what actually works for live hosts.

✅ Closing — Your Troubleshooting Order

When your Windrose server "is built but something is wrong," do not randomize settings. Follow this authoritative order every time, because it isolates the layer that is actually broken:

1. Read the logs. The first error names the problem. 2. Port forward 3478 UDP+TCP on the router, and confirm you are not behind CG-NAT. 3. Open the firewall for both protocols plus the executable. 4. Fix config mistakes — blank PublicIP, MaxPlayers ≥ 1, ASCII-only names, matching Port/PublicPort. 5. Rule out version/mod conflicts by comparing build numbers and standardizing mod load order. 6. Only then reinstall if a verified-corrupt asset is named in the log.

The real gap in Windrose's server documentation is not "how to install" — it is everything after installation, when the server runs but refuses to behave. The official pages contradict each other on the two most important points (TCP requirement and PublicIP), which is exactly why so many hosts get stuck. Use the order above, trust the log over the wiki, and your friends will be sailing the archipelago tonight.
