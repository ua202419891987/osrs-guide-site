🔍 1. What "Failed to Connect" Actually Means

Before you touch a single setting, understand the message. In Windrose, "Failed to Connect" is a catch-all client error. It appears whenever your game client attempts to contact a server (host) and the handshake never completes within the timeout window. The client does not know why — it only knows the connection did not succeed — so it prints the same generic line whether the server is powered off, the port is closed, or your firewall ate the packet.

This is why blindly "restarting the game" fixes it maybe 1 time in 10. You are not dealing with one bug; you are dealing with a category of failure. The good news: the causes are well understood, and they are almost always on the host side or the network path between you and the host, not inside the game files themselves.

First move — read the error code: Windrose logs a short code next to the failure in the bottom-left of the connect screen. ERR_TIMEOUT usually means a closed port or firewall. ERR_REFUSED usually means the server process is not running. ERR_VERSION means a version or mod mismatch. Write down the code before you start changing things — it tells you which section of this guide to jump to.

The table below maps each code to its most likely cause so you can skip straight to the relevant fix:

The official tutorial gap: Windrose's in-game "Host a Server" tutorial walks you through creating a world and inviting friends, but it never mentions port forwarding, firewall exceptions, the UDP-vs-TCP difference, or IPv6. Hundreds of players hit "Failed to Connect" the first time they try cross-network co-op specifically because that documentation is unfinished. Every gap below is filled in this guide.

✅ 2. Quick Checklist — 7 Things to Check

If you want the fastest possible path to a working connection, run through this numbered checklist top to bottom. Each item is ordered from "most common and easiest to fix" to "rarer and more involved." Roughly 85% of "Failed to Connect" reports are resolved by items 1 through 4 alone.

1

Confirm the server is actually running

On the host machine, open Windrose and verify the world is listed as "Online" in the server manager — not paused, not in the main menu. A powered-off or paused host returns ERR_REFUSED instantly. If the host crashed, relaunch it and watch for a crash message.

2

Verify both players are on the identical game version

Open the main menu on both machines and compare the build number in the bottom-right corner. A mismatch triggers ERR_VERSION. If one player just updated and the other did not, sync them through Steam (or your platform's update check) before retrying.

3

Check UDP port 3478 forwarding on the host router

This is the single biggest fix. Windrose uses UDP port 3478, not TCP. Log into the host router, forward UDP 3478 to the host PC's internal IP, and save. Many players forward TCP 3478 by mistake and still fail — the protocol matters.

4

Add Windrose to the host firewall allow-list

Windows Defender (and most third-party antivirus suites) block Windrose's network traffic by default. Create inbound AND outbound rules for Windrose.exe on both TCP and UDP. Do this on the host machine first; if the client also runs a strict firewall, repeat it there.

5

Test IPv4 vs IPv6 parity

Have the host and client each visit a "what is my IP" site. If one is IPv6-only and the other is IPv4-only, the connection can silently fail. Force both to IPv4 in router settings, or have the client connect via the host's IPv4 address directly instead of a hostname.

6

Flush the DNS cache and check the hosts file

On the client, run ipconfig /flushdns in a terminal. Then open C:\Windows\System32\drivers\etc\hosts and confirm there is no stale or erroneous entry pointing the Windrose server name to the wrong address. A single bad line here breaks connections that "should" work.

7

Disable mods temporarily to rule out conflicts

If the host runs mods and the client does not (or vice versa), the connection is refused. Temporarily move both players' Mods folders aside, launch vanilla, and test. If it connects clean, re-add mods one at a time to find the offender.

Power-user shortcut: If you just want to confirm the network path works before debugging the game, have the client open a terminal and run telnet <HOST_IP> 3478 (or Test-NetConnection on PowerShell). If the port does not respond, the problem is the router/port forward, not Windrose. This single test eliminates half the possible causes in ten seconds.

🖥️ 3. Cause 1: Server Is Offline / Not Running

The simplest cause is also the most embarrassing one to overlook: the server is simply not up. In Windrose, "hosting" means the host's own game client is actively running the world. If the host closed the game, alt-tabbed into a paused state, or the server process crashed, every join attempt returns ERR_REFUSED almost immediately.

Common failure modes here include: the host launched the world but then the game auto-updated and restarted (dropping the session), the host's PC went to sleep after idle, or a background crash silently closed the process. Always confirm the host sees the world as "Online" before the client retries.

🛠️ How to confirm the server is live

On the host: Open the server manager (main menu → Multiplayer → My Servers). The target world should show a green "Online" dot. If it shows "Offline" or "Paused," select it and click "Resume" or "Start."
On the client: Before joining by IP, ask the host to read you the server's status. If they say "it's running but I'm in the main menu," that is the bug — the world must be actively hosted, not merely exist on disk.
Crash check: If the host game closed unexpectedly, check the crash log at %USERPROFILE%\AppData\Local\Windrose\Saved\Crashes. A recurring crash here points to a corrupt save or an incompatible mod, not a network issue.

Sleep mode trap: Windows power settings frequently put the host PC to sleep after 15–30 minutes of inactivity. A sleeping PC cannot host. On the host, go to Control Panel → Power Options and set "Put the computer to sleep" to "Never" while hosting. This alone resolves a surprising number of "it worked earlier, now it fails" reports.

🔌 4. Cause 2: Port 3478 Not Forwarded

This is the cause behind the majority of "Works on my LAN but not over the internet" complaints. When the client and host are on the same home network, they talk directly and never touch the router's port rules — so co-op "works" locally. The moment a friend tries to join from outside the network, the router must forward incoming traffic on the game port to the host PC. If that rule is missing or wrong, the packet is dropped and the client sees ERR_TIMEOUT.

Windrose uses UDP port 3478 for its connection layer. This is the detail that breaks most guides: players follow a generic "port forward" tutorial that forwards TCP, and UDP never gets opened. The connection still times out because the right protocol is closed.

1

Find the host PC's internal IP

On the host, open a terminal and run ipconfig (Windows) or ifconfig (Linux/mac). Note the IPv4 address under the active adapter — typically something like 192.168.1.50. This is the destination your router needs.

2

Log into your router

Open a browser and go to your router's gateway address (commonly 192.168.1.1 or 192.168.0.1). Log in with the admin credentials printed on the router or provided by your ISP. Navigate to "Port Forwarding," "NAT," or "Virtual Server."

3

Create the UDP 3478 rule

Add a new rule: Protocol = UDP, External Port = 3478, Internal Port = 3478, Destination IP = the host's internal IP from step 1. Save and reboot the router if prompted. Do NOT select "TCP" or "Both" and assume it covers UDP — explicitly choose UDP.

4

Assign a static internal IP to the host

Routers often reassign internal IPs after a reboot, which silently breaks your forward. In the router's DHCP reservation (or static lease) settings, bind the host's MAC address to a fixed IP so port 3478 always reaches the right machine.

Double-NAT warning: If your host sits behind two routers (for example, an ISP modem/router combo plus your own Wi-Fi router), you must forward 3478 UDP on both devices, or put the inner router in bridge mode. A single forward through only one device still drops the packet. This is the most commonly missed sub-step in port-forwarding guides.

🛡️ 5. Cause 3: Firewall Blocking

Even with a perfect port forward, a firewall sitting on the host (or the client) can intercept and discard Windrose's packets before they ever reach the game. Windows Defender Firewall blocks unknown executables by default, and third-party antivirus suites are even more aggressive. The symptom is identical to a closed port: ERR_TIMEOUT after the usual spin.

The key mistake players make is adding only an inbound rule. Windrose's netcode opens return connections, so you need both inbound and outbound allowances. Add the rule for Windrose.exe covering both directions and both protocols.

🪟 Windows Defender allow-list (host machine)

1. Open "Windows Defender Firewall" → "Advanced settings."
2. Select "Inbound Rules" → "New Rule" → "Program" → browse to Windrose.exe → "Allow the connection" → check Domain, Private, Public.
3. Repeat for "Outbound Rules" with the same executable.
4. Name it clearly (e.g., "Windrose MP In" / "Windrose MP Out").
5. Retry the connection. If it now works, the firewall was the blocker.

Third-party antivirus: If the host runs Norton, McAfee, Bitdefender, or similar, Defender rules alone will not help — those suites insert their own network filter. Open the suite's firewall section and add Windrose.exe to the allowed applications list, or temporarily disable the suite's firewall (not the whole antivirus) for a quick test. Re-enable it afterward with the exception in place.
Client-side too: Do not forget the joining player's firewall. If the host is perfectly configured but the client's outbound traffic is blocked, the handshake still fails. Run the same allow-list steps on the client PC. The fastest diagnostic: temporarily disable both firewalls, test the join, then re-enable with proper rules once confirmed.

🌐 6. Cause 4: IPv6 vs IPv4 Mismatch

Modern networks increasingly run dual-stack (both IPv4 and IPv6), and this is where Windrose's connection layer gets finicky. If the host is reachable only over IPv6 while the client is on a legacy IPv4-only connection (or the reverse), the two can fail to negotiate a path even though both have "internet." The result is the classic "connects, then drops after a few seconds" or a flat ERR_TIMEOUT with no clear cause.

This is notoriously hard to spot because the server browser may show the host as "available" — the listing travels over a different channel than the actual game data. The fix is to force both ends onto a common protocol.

🔧 Forcing IPv4 parity (recommended)

1. On both the host and client, open the network adapter settings and temporarily uncheck "Internet Protocol Version 6 (TCP/IPv6)", leaving IPv4 enabled. This forces both machines onto IPv4, which Windrose handles most reliably.
2. Reboot both PCs (or run ipconfig /release && ipconfig /renew).
3. Have the client connect using the host's IPv4 address directly (e.g., 192.168.1.50:3478 for LAN, or the public IPv4 for internet) rather than a hostname or invite link.
4. If it connects, IPv6 was the culprit. You can leave IPv6 off while playing, or investigate router-level IPv6 pass-through later.

Use the raw IP, not the invite link: Windrose's friend-invite system sometimes resolves through a relay that prefers IPv6. Pasting the host's actual IPv4 address into the "Join by IP" field bypasses that resolution layer entirely and is the most reliable way to test a suspected IPv6 issue.
ISP CGNAT caveat: Some ISPs place customers behind Carrier-Grade NAT, meaning your "public" IPv4 is shared and not directly reachable from outside. If port 3478 is correctly forwarded but external friends still cannot reach you, ask your ISP whether you are behind CGNAT. The workaround is a VPN-based LAN tool (see Last Resort) or requesting a public IPv4 / IPv6 allocation from the ISP.

📝 7. Cause 5: Hosts File / DNS

Less common but maddening when it happens: a corrupted hosts file or a stale DNS cache on the client can route the server name to the wrong (or no) address. This produces connections that "should" work — the IP is correct, the port is open, the firewall is fine — yet the client still fails. The issue is name resolution happening before the connection attempt.

The hosts file is a plain text file on Windows that overrides DNS for specific names. A leftover or mistyped entry from a previous game, VPN, or mod can silently hijack the server hostname. Even without a bad entry, a stale DNS cache can hold an old, unreachable address.

🧹 Flush DNS and inspect the hosts file (client machine)

1. Open a terminal as administrator and run ipconfig /flushdns. This clears cached bad lookups.
2. Open Notepad as administrator, then open C:\Windows\System32\drivers\etc\hosts (no file extension).
3. Look for any line referencing your server's hostname or a Windrose-related domain. If you do not recognize it, comment it out by prefixing the line with #.
4. Save and retry. A clean hosts file plus a flushed cache resolves the "mysterious intermittent" connection failures.

Public vs private DNS: Some custom DNS providers (and certain pi-hole setups) block or mis-route gaming server domains. As a quick test, switch the client's DNS to a major public resolver (e.g., 1.1.1.1 or 8.8.8.8) and retry. If that fixes it, your local DNS filtering was the culprit — whitelist the Windrose server domain rather than abandoning your filter.

⚙️ 8. Cause 6: Mod or Version Conflict & Last Resort

The final common cause is a mismatch between what the host is running and what the client has. Windrose enforces version parity, so a different build number triggers ERR_VERSION. Mods are stricter: if the host loads a mod the client lacks (or vice versa, or the mod versions differ), the connection is refused even when base versions match. This is the #1 reason a group that "played fine yesterday" suddenly cannot connect after one person subscribed to a new mod.

🧩 Resolving mod / version conflicts

1. Compare build numbers on both main menus (bottom-right). If they differ, update the behind player through Steam / the platform client.
2. On both machines, open the Mods manager and confirm the enabled mod list and versions are identical. Windrose does not auto-sync mods between players.
3. If unsure, move both players' Mods folder to the desktop, launch vanilla, and test. A successful vanilla join proves a mod conflict.
4. Re-add mods one at a time on BOTH machines simultaneously until the offender is isolated, then either remove it or ensure both players run the matching version.

Save-version lockstep: A host running a newer game version may have saved the world in a format the older client cannot read — even after you "fix" the connection, the client could desync or crash on join. Always update everyone together. There is no partial-compatibility mode in Windrose Early Access.

🆘 Last Resort — If Nothing Works

If you have worked through every section above and the connection still fails, you are almost certainly hitting an environment problem that port forwarding alone cannot solve — usually CGNAT, a strict corporate/school network, or an ISP that blocks inbound UDP. These are the options that finally get stubborn setups working:

A

Use a VPN-based virtual LAN (ZeroTier / Radmin / Hamachi)

These tools create a private network tunnel that makes remote friends appear to be on the same LAN. Install the same VPN client on host and client, join a shared network, and connect using the VPN-assigned IP. This completely bypasses router port forwarding and CGNAT — it is the most reliable fix for "nothing else worked."

B

Have the client host instead

Network asymmetry is real: the host's ISP may block inbound traffic while the client's does not. Swap roles and test. If the reverse direction connects, the original host's network is the wall — keep the more permissive network as host, or use option A.

C

Try the official dedicated server tool

Windrose offers a headless dedicated server build that behaves more predictably than in-client hosting for some routers. Run it on a always-on machine, forward 3478 UDP to that box, and connect by IP. Many "in-client hosting fails but dedicated works" cases are caused by the game client's firewall interaction, which the headless build avoids.

D

Gather logs and report with detail

If all else fails, collect the host's Windrose.log (from %USERPROFILE%\AppData\Local\Windrose\Saved\Logs) and the client's connection error code, then post in the official Discord with your router model, ISP, and whether CGNAT applies. Include the exact error code — it is the difference between a guess and a real fix.

Order of last resort: Try B (swap host) first — it takes two minutes. If that fails, go to A (VPN LAN), which solves ~90% of remaining cases including CGNAT. Reserve C and D for when you want a permanent, repeatable setup or need developer help.

❓ FAQ — "Failed to Connect" Questions

Q: Why does it say "Failed to Connect" with no error code?

Windrose sometimes omits the code on the visible dialog even though it is logged. Open the client log at %USERPROFILE%\AppData\Local\Windrose\Saved\Logs\Windrose.log right after a failed attempt and search for "Connect" or "NetError" — the code is there. The most common silent failure is a closed UDP 3478 port (treated as timeout).

Q: It works on my home LAN but my friend outside can't join. What's wrong?

That is the textbook port-forwarding symptom. LAN traffic never touches the router's forward rules, so it works locally; internet traffic does. Forward UDP port 3478 to the host's internal IP on the router (see Section 4). If your ISP uses CGNAT, you will also need the VPN-LAN approach from Last Resort.

Q: I forwarded TCP 3478 and it still fails. Why?

Windrose uses UDP, not TCP, for its connection layer. A TCP forward leaves the actual game port closed, so the client times out. Delete the TCP rule and create a UDP 3478 forward instead. The protocol selection in your router's port-forward screen matters more than the number.

Q: Do mods really block connections even if the base game version matches?

Yes. Windrose checks the enabled mod list and each mod's version during handshake. A single mod present on the host but missing on the client (or a version difference) causes an immediate refusal, independent of the base build number. Both players must run an identical mod set and versions, or none at all.

Q: My ISP said I'm behind CGNAT. Can I still host?

Not via standard port forwarding — CGNAT gives you a shared public IP you cannot forward through. Your reliable options are: (1) a VPN-based virtual LAN (ZeroTier, Radmin, Hamachi) which tunnels past CGNAT, or (2) asking your ISP for a public IPv4/IPv6 allocation (sometimes a paid add-on). Most players solve it with option 1 in under ten minutes.

Q: The connection drops a few seconds after joining. What causes that?

Intermittent drops usually point to an IPv6/IPv4 path mismatch or an unstable network route, not a hard block. Force both host and client to IPv4 (Section 6), connect by raw IPv4 address, and flush the DNS cache. If drops persist only under load, also check for packet loss with a continuous ping to the host during a session.

Q: Is there an official guide that covers all this?

Partially. Windrose's official "Host a Server" tutorial covers creating and inviting but omits port forwarding, firewall rules, the UDP-vs-TCP detail, IPv6 handling, hosts-file fixes, and mod parity. This guide was written specifically to fill those gaps — the sections above cover every cause the official docs leave out.
