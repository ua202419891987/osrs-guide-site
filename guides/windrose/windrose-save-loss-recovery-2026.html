Windrose Save Lost? World Disappeared? Full Recovery Guide (2026)

Emergency Fix

"Umm, my game is gone." Your world vanished from the load menu, or a boss-death crash ate an hour of progress. Here is the exact recovery order — local rollback files, Steam Cloud, Windows shadow copies — plus the 5-minute auto-backup setup that makes this the last time it happens.

🎮 Emergency Fix · 8 min read · Updated August 2026

⏱️ Quick Summary — 30-Second Read

  • 📌 Stop playing immediately. Every new session overwrites the rollback copy that would have saved you. Close Windrose before you troubleshoot anything.
  • 📌 90% of "world disappeared" cases are not deleted saves — they are a Steam Cloud conflict or a zero-byte write that hides the entry from the load menu. The data is usually still on disk.
  • 📌 Recovery order that works: local .bak/rollback file → Steam Cloud rollback → Windows Previous Versions (shadow copy) → recycle bin/undelete.
  • 📌 Prevention beats recovery. A 5-line scheduled copy job snapshots your world folder every 15 minutes and costs about 2 MB per snapshot.

1. 60-Second Triage — What NOT to Do First

The most common way players permanently lose a Windrose world is not the bug — it is what they do in the ten minutes after it. Windrose keeps a small number of rollback copies alongside your live save, and every launch advances that rotation, pushing your last-known-good copy closer to being overwritten. Panic-clicking turns an 80% recoverable situation into a 0% one.

Do these four things right now, in this order:
(1) Quit Windrose completely — check Task Manager and end any lingering Windrose-Win64-Shipping.exe process.
(2) Set Steam to Offline Mode (Steam → top-left menu → Go Offline). This stops the cloud from pushing an empty save over your good local one.
(3) Do NOT verify game files. Verification will not restore saves and can trigger a cloud re-sync that overwrites them.
(4) Do NOT create a new world with the same name. Same-name worlds can land in the same folder and bury the recoverable data.

With the game closed and Steam offline, nothing is racing you. Copy the whole save directory (section 2) to your Desktop before touching anything — every step from here happens on the copy, never the original.

2. Where Windrose Actually Stores Your World

Windrose is an Unreal Engine title, so it follows the standard UE save layout rather than putting worlds in the Steam install folder. That is why players who search steamapps find nothing and conclude the save is gone. It was never there. Paste these into the Explorer address bar:

WhatPathWhat you'll see
Live world saves%LOCALAPPDATA%\Windrose\Saved\SaveGamesOne .sav per world, plus profile/settings files
Rollback / temp writesSame folder.bak, .tmp, .sav.old, or numbered copies
Crash logs (diagnosis)%LOCALAPPDATA%\Windrose\Saved\LogsWindrose.log and dated backups
Steam Cloud mirrorSteam\userdata\<SteamID>\<AppID>\remoteCloud copy of the same saves
Dedicated server worldsServer install folder → Saved\SaveGamesHost-side world, separate from your client
Read the file sizes — fastest diagnosis in this guide. A healthy mid-game world is a few hundred KB to several MB. If your .sav shows 0 KB, the game was interrupted mid-write and left an empty header. That is exactly the "world vanished from the menu" symptom: the file exists, the launcher can't parse it, so it isn't listed. The 0 KB file is dead — but the .bak beside it usually isn't.

Sort by Date modified and screenshot the list; those timestamps tell you how much progress any given restore will cost. In co-op, your client copy and the host's copy are different files — see our Windrose co-op setup & troubleshooting guide for which machine is authoritative.

3. Recovery Method 1-4 — Ranked by Success Rate

Work top to bottom. Do not skip ahead — each method is less likely to succeed and costs more progress than the one above it.

Method 1 — Restore the local rollback file (success rate: highest)

In SaveGames, look for your world's name with an extra extension: MyWorld.sav.bak, .tmp, or MyWorld_backup.sav. Move the broken MyWorld.sav to your Desktop, then rename the rollback to exactly MyWorld.sav — turn on "show file extensions" first or you'll create MyWorld.sav.bak.sav. Launch with Steam still offline. The world usually reappears 5-20 minutes behind where you left off.

Method 2 — Roll back through Steam Cloud (success rate: high)

If nothing local is usable, the cloud copy may predate the corruption. Steam hides old versions in the client but exposes them on the web: open store.steampowered.com/account/remotestorageapp/?appid=<Windrose AppID> while logged in for a dated file list with per-entry download links. Grab the version from before the incident and drop it into SaveGames while still offline. Re-enable online mode only after the world has loaded and saved once — that first save is what marks your local copy "newer" so the cloud won't overwrite it.

Method 3 — Windows Previous Versions / shadow copy (success rate: medium)

Right-click the SaveGames folder → Properties → Previous Versions. If System Protection or File History is enabled on that drive, Windows has silently kept folder snapshots. Restore to a separate location (never "Restore" in place — that overwrites your only evidence), then copy the world file across manually. This works far more often than players expect, because OneDrive-synced user folders and default File History setups both quietly cover %LOCALAPPDATA% on many machines.

Method 4 — Undelete (success rate: low, but free)

Check the Recycle Bin first — an anti-virus or cleanup tool may have quarantined the file. If not, run a free undelete tool (Recuva, PhotoRec, or Windows File Recovery) against the drive holding %LOCALAPPDATA%. Critical rule: write the recovered output to a different drive. Recovering onto the same drive can overwrite the very sectors that hold your world. Also stop installing/downloading anything on that drive until you're done.

If all four fail: the world is gone, and rebuilding is the only path. Before you rage-quit, know that a returning player with map knowledge reaches mid-game dramatically faster than a first-timer — our Windrose progression guide has a compressed route that skips the exploratory dead ends. And this time, set up section 5 first.

4. The Boss-Death Crash: Losing 1 Hour of Progress

A separate and far more common flavour of "save loss" is not file corruption at all. It is the Early Access autosave cadence colliding with a hard crash. Players repeatedly report the same pattern: the health bar hits zero — a boss first-kill attempt, a fall, a drowning — and instead of the death screen the game hard-freezes or CTDs. On relaunch, the world loads at a state up to an hour older, because the last successful autosave happened before the whole boss run.

The mechanism matters, because it changes the fix. When the game crashes at the exact instant of the death transition, it never gets to flush the death state — and in Windrose's current build, several progression writes (loot picked up, recipes unlocked, structures placed) are only committed on autosave or on a clean exit. Nothing was corrupted; it simply was never written.

Force a save before anything risky

The reliable manual commit is a clean Save & Quit to Main Menu — not Alt+F4, not closing the window. Do it before: your first pull on any new boss, before entering a new biome, after any big build session, and after any large loot haul. It costs about 20 seconds and converts a potential one-hour loss into a zero-minute loss. Treat it as a habit, the same way you'd repair your ship before a long voyage.

Two supporting habits cut the damage further. First, do not carry your entire inventory into a first boss attempt — if the crash also drops your bag, recovery gets ugly fast, and the rules for that are covered in our Windrose death & loot recovery guide. Second, if your crash-on-death happens every single time rather than occasionally, that is a stability problem, not a save problem — check crash logs in Saved\Logs for a repeating GPU or asset error before you blame the save system.

5. Never Again — The 5-Minute Auto-Backup Setup

Early Access survival games write saves aggressively and validate them lightly. Rather than hoping the next patch fixes it, spend five minutes making loss structurally impossible. A full Windrose world is small — snapshots cost almost nothing.

Step 1 — Create the snapshot script

Open Notepad, paste the two lines below, and save as windrose-backup.bat (set "Save as type" to All Files):

set STAMP=%date:~-4%%date:~3,2%%date:~0,2%-%time:~0,2%%time:~3,2%
robocopy "%LOCALAPPDATA%\Windrose\Saved\SaveGames" "D:\WindroseBackups\%STAMP: =0%" /E

Change D:\WindroseBackups to any folder on a different physical drive than your game — a drive failure that takes your save should not take the backup with it.

Step 2 — Schedule it every 15 minutes

Open Task Scheduler → Create Basic Task → name it "Windrose Backup" → Trigger: Daily → then in the finished task's Properties → Triggers → Edit → tick Repeat task every 15 minutes for a duration of Indefinitely. Action: Start a program → browse to your .bat. Tick "Run whether user is logged on or not" only if you want it silent.

Step 3 — Keep a manual "milestone" copy

Automated snapshots roll. Before every genuinely irreplaceable moment — a finished mega-base, a boss unlock, the end of a long co-op session — copy the world file once by hand into a folder named after the milestone. This is your never-deleted floor. If you build large, this pairs directly with the maintenance routine in our Windrose building QoL workarounds guide, since heavy bases are exactly the saves you cannot afford to lose.

Step 4 — Verify the backup actually works

Untested backups fail when you need them. Once, deliberately: rename your live .sav, restore a snapshot, confirm the world loads, then swap back. Ninety seconds of testing tells you whether your safety net is real.

Retention math: at 15-minute intervals and roughly 2-5 MB per world, a week of snapshots costs well under 2 GB. Add a monthly cleanup that deletes folders older than 14 days and you can leave this running forever without thinking about it again.

FAQ

Q: My world vanished from the menu but the file is still in SaveGames. Why?

The launcher only lists worlds whose headers it can parse. A 0 KB file, a partially written file, or one with a mismatched build version parses as invalid and is silently skipped rather than shown as an error. Restore the .bak (Method 1) and it will reappear.

Q: Will verifying game files through Steam bring my save back?

No. Verification only checks installed game files against Steam's manifest; saves are not part of that manifest. It can, however, kick off a cloud sync that overwrites a local file you were about to recover. Avoid it while troubleshooting.

Q: Should I disable Steam Cloud for Windrose permanently?

No — cloud is a second copy and it has saved plenty of worlds. Just disable it temporarily during a recovery so it can't overwrite your working files, then turn it back on after your restored world has saved successfully once.

Q: I play co-op. Whose machine has the real save?

Whoever hosts the world holds the authoritative file — guests keep only character data, not the world. If the host's save is lost, the world is lost for the whole group, so the host should be the one running the backup script. Hosting specifics are in the co-op troubleshooting guide.

Q: Can I edit the save file to undo a bad event?

Not reliably. Windrose save data is packed binary; hand-editing usually produces a file the game rejects, and there is no community-maintained editor with a good safety record yet. Restoring an earlier snapshot is safer and faster.

Q: A patch dropped and now my old world won't load. Is it corrupted?

Probably not — it's a version mismatch. Try rolling the game back to the previous build via Steam betas if the developer exposes one, load the world, do a clean Save & Quit, then update again. Always take a manual milestone copy before applying any Early Access patch.
