Windrose Co-op Setup & Troubleshooting: From "Can't Connect" to Onboard

Multiplayer & Networking
⚓ Level: All Players

Windrose has no server browser, no quick-match and no in-game error codes worth reading. This is the complete decision tree — every gate between launching the game and standing on your friend's deck, in the order they actually break.

🎮 Windrose Guide · 10 min read · Updated August 2026
Published: August 3, 2026

⏱️ Quick Summary — 30-Second Read

  • 📌 Both players must finish the tutorial first (15–20 minutes). Co-op is hard-locked behind it, and this is the number one reason an invite code appears to "do nothing".
  • 📌 Build numbers must match exactly. Not "both updated" — the same build string. A single player on a beta or delayed-download build fails silently with no mismatch warning.
  • 📌 There is no server browser. Invite codes are the only join path. Codes are session-bound and die the moment the host returns to the main menu.
  • 📌 Network layer: allow UDP 3478 outbound (plus its neighbours 3479–3481) and get off strict/symmetric NAT. In mainland China, an accelerator with UDP forwarding is effectively mandatory.

1. Prerequisites — The Four Hard Gates

Most "Windrose co-op is broken" threads are not network problems at all. They are players tripping over one of four requirements that the game never explains clearly. Clear all four before you touch a router setting.

Gate 1 — Tutorial completion (both players)

Co-op does not unlock until the opening tutorial sequence is complete, which takes roughly 15–20 minutes per player. A player who has not finished it can hold a valid invite code and still be refused, usually with a generic failure rather than a clear message. If you plan a co-op night, have everyone clear the tutorial in advance rather than burning the first half hour of your session on it.

Gate 2 — Exact build match

Windrose is strict about version parity in Early Access. Patches land frequently and clients do not all download at the same moment. Both players must be on the identical build; being "on the latest" is not enough if one client has not finished updating. Verify the build string on the main menu before troubleshooting anything else.

Gate 3 — Invite code only

There is no server browser and no friends-list quick join. The host generates a session code and the joining player enters it manually. Codes are tied to the live session — if the host quits to the main menu, reloads a different save, or crashes, the old code is dead and a new one must be generated.

Gate 4 — Host stability

The host machine is the server. Its upload bandwidth, CPU and save integrity determine everyone's experience. Choose the host by connection quality, not by who owns the most progressed save. If the host's world has a history of corruption or long load times, resolve that first using our save loss and recovery guide — hosting an unstable world is how a whole group loses an evening.

Order matters. Do not start forwarding ports until gates 1–3 are confirmed. Roughly two thirds of failed connections in community reports resolve at the tutorial or version gate, and port changes made while chasing the wrong cause just add variables you will have to unwind later.

2. The Full Troubleshooting Decision Tree (Exclusive)

Work top to bottom and stop at the first branch that matches your symptom. This is the sequence that resolves the widest range of cases with the fewest changes — and it is the piece no competitor page provides, because they list settings rather than an order of operations.

Branch A — The invite code is rejected as invalid

Cause is almost always a stale code or a typo in an ambiguous character. Have the host regenerate the code while the world is loaded and paste it through chat rather than reading it aloud — 0/O and 1/I cause a surprising share of failures. If a freshly pasted code still fails, the joining player has not cleared the tutorial (Gate 1).

Branch B — Code accepted, then it hangs on "connecting"

This is the network layer. The handshake started and the peer-to-peer negotiation failed. Go to section 3: open UDP 3478, check NAT type, and if you are in mainland China enable your accelerator's UDP mode. A hang that times out after roughly 60–90 seconds is the classic NAT traversal failure signature.

Branch C — Connects, then drops during the loading screen

Usually version mismatch (Gate 2) or a host-side world problem. If both builds match, have the host load the world alone first and confirm it reaches a playable state before inviting anyone. A world that loads slowly solo will frequently time out a joining client.

Branch D — In the world but everything rubber-bands

You are connected; this is bandwidth or latency. Ask everyone else in the household to stop large downloads, and have the host close background streaming. Persistent desync also degrades naval gunnery badly — if your shots stop landing, cross-reference the cannon hit registration guide, because joining clients register measurably fewer hits than the host.

Branch E — One specific friend can never join, everyone else can

The problem is on their end, and it is almost always strict or symmetric NAT from a carrier-grade NAT connection (common on mobile broadband and some campus networks). Options: have that player host instead, have them switch to a different network, or use a UDP-capable accelerator. No amount of host-side configuration fixes a symmetric NAT on the other end.

3. Ports, NAT and Accelerators

Windrose uses UDP 3478 for its session negotiation — the standard STUN/TURN port range. If your firewall or router blocks it, the code will be accepted and the connection will then quietly fail.

Mainland China players: a game accelerator is effectively required, and the critical detail is that it must forward UDP traffic. Many tools default to TCP acceleration, which is enough to reach the store and the login layer but will not carry the co-op session. Both host and joining player should run the same accelerator with the same node region where possible — mismatched routing regions add latency that can push the handshake past its timeout.

Fastest diagnostic: have the host mobile-tether their phone and try again. If it connects instantly over tethering, the problem is the home router's NAT or firewall, not the game. This two-minute test saves an hour of port forwarding on the wrong device — and it is the check almost nobody runs first.

4. You Are In — Now Stop It Breaking

Getting connected is half the job; staying connected through a three-hour session is the other half. Establish these habits from the first night.

Always the same host. Co-op progress lives in the host's world file. Rotating hosts splits your group's progress across saves that can never be merged. Pick one host and stick to them for the whole playthrough.

Back up the host world before each session. Copy the save folder somewhere safe. Multiplayer sessions increase write frequency and therefore corruption risk; a five-second copy is the cheapest insurance in the game.

Agree on a disconnect protocol. If someone drops mid-fight, the remaining players should retreat rather than push. A disconnected player's body and inventory follow the normal death rules, so read the death and loot recovery guide before you find out the hard way what happens to a crewmate's gear when they time out during a boarding action.

Regenerate codes deliberately. If someone needs to rejoin, the host should stay in-world and reissue the code. Quitting to the menu to "reset" the session kills the code for everyone still connected.

FAQ

Q: Do both players really need to finish the tutorial?

Yes. Co-op access is gated behind tutorial completion for every participant, and it takes 15–20 minutes each. This is the single most common cause of an invite code that appears to be broken.

Q: Is there a server browser or public matchmaking?

No. Windrose currently supports invite codes only. There is no public listing, no quick-match, and no persistent lobby — the code is generated per session and expires when the host leaves the world.

Q: Which port does Windrose co-op use?

UDP 3478 is the primary session port, with 3479–3481 acting as fallbacks. Allow the game through both the Private and Public Windows Firewall profiles; the Public profile is enabled by default on many laptops and silently blocks the handshake.

Q: Can players on different patch versions play together?

No. The build must match exactly. Because there is no clear mismatch warning, this failure looks identical to a network problem — always compare build strings before changing router settings.

Q: Does progress carry over if a different person hosts next time?

No. The world lives on the host machine. Switching hosts means starting from that person's separate save, and there is no merge function. Choose your host on connection quality on night one and keep them.

Q: Why does co-op work for two players but fail with a third?

Usually the host's upload bandwidth or a NAT limitation on the third player's connection. Add players one at a time and note which addition breaks the session — that isolates whether it is a capacity issue or one specific connection.
