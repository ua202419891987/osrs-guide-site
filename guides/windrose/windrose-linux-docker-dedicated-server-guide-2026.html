Why Run a Dedicated Server at All

In a normal hosted session, the person who opens the world is the world: that one machine simulates ship physics, boarding NPCs, every placed structure, farms and quest state for everyone. Our Host Performance & 8-Player Guide breaks down exactly what that costs. A dedicated server moves that job to a machine whose only responsibility is running the world.

Three concrete things you gain:

  • The world persists. Nobody has to be at their PC. Friends can play at 2am in your time zone without you leaving a machine on in your bedroom.
  • The host-player's frame rate stops being a shared resource. The person who used to host can now just play, like everyone else.
  • You can change world settings. World configuration lives in a world description file — which is a dedicated-server capability, and the reason the 0.10.0.6 fix below mattered so much.
Who actually needs one: groups larger than about four players, groups spread across time zones, and any group whose world has accumulated enough building that the host's frame rate suffers. Solo players and pairs hosting on a decent gaming PC usually do not.

It is worth being honest about the trade too: a dedicated server is something you now maintain. There are updates to apply, a world to back up, and a box that can be misconfigured. Do not stand one up because it sounds impressive — stand one up because your group hit one of the three gains above.

Two Blockers That Only Recently Cleared

Dedicated servers in Windrose have a short and slightly awkward history, and knowing it saves you from following outdated advice.

WorldDescription.json could not be edited — fixed in 0.10.0.6

For a period, running a dedicated server meant you could not modify the world description configuration. You could stand the server up, but the world settings were effectively locked — which defeated a large part of the reason to run one in the first place. Patch 0.10.0.6 fixed this. If you are on a build at or after 0.10.0.6, editing your world settings on a dedicated server is expected to work; if something still will not stick, confirm your server build first before assuming you did it wrong.

Linux support arrived in 0.10.0.7 — as a Docker image

Linux dedicated server support landed in patch 0.10.0.7 (late June), and it is delivered as a Docker image rather than a bare tarball or a package. Before that, the practical option for a dedicated server was Windows. If you are reading a guide that assumes a native Linux binary and a manual startup script, it predates this.

Do not copy-paste deployment commands from old guides or forums. Because Linux support shipped as a Docker image in a specific patch, the exact image name, tags, volume mount paths and environment variables are defined by the official image documentation for the build you are running. They change between patches. Treat any exact command you find elsewhere as a starting point to verify, not as truth.

The practical consequence of the Docker delivery model is good news: you do not need to care much which distro you run. Anything that runs a current Docker engine will do. The thing that actually varies between builds is the image itself and how it expects to be configured.

Before You Deploy: Requirements & Decisions

Decide these four things before you touch a terminal. Changing your mind later usually means rebuilding the world.

1

Where the box lives

A home machine, a spare mini-PC, or a rented VPS/cloud instance. A home box is free and fine for a small group if your upload is decent; a VPS costs money but gives you a stable address and someone else's uptime. For a group spread across regions, latency to the server matters more than raw CPU.

2

How much world you are going to run

Server load scales with player count and with how much your group has built. A four-player world with one tidy base is a very different machine from an eight-player world with five sprawling plots. Entity count is the dominant cost — see our Server Entity Bloat & Lag Fix Guide.

3

Persistent storage, outside the container

Your world must live in a mounted volume or a host directory, not inside the container filesystem. A container is disposable; your world is not. If the world data lives only in the container, the next image update is a world deletion.

4

Networking and port forwarding

Players have to be able to reach the server. Forward the ports the server actually uses on your router or cloud firewall, and confirm from outside your own network that it is reachable. Port work is its own subject — our Port 3478 Dedicated Server Forwarding Fix covers the dedicated-server side, and the Port 3478 Co-op Player Fix covers the client side.

Also decide now who is the administrator. Somebody needs to own updates and backups, and "everybody" is not an answer that survives contact with a corrupted save.

Docker Deployment — The General Flow

The steps below are deliberately generic. Exact image names, tags, environment variables, mount paths and command-line flags are defined by the official image documentation for the specific build you are running, and they do change between patches — so check the official image instructions alongside this and treat them as authoritative over anything you read here.

1

Install a current Docker engine

Use your distribution's supported method or Docker's own repository. Confirm the install works before continuing, and make sure the Docker service starts on boot — a server that does not come back after a reboot is not a server.

2

Create a host directory for world data

Make a dedicated directory on the host for the server's persistent data (world save, configuration, logs). Give it to the user the container runs as, so the server can actually write to it. This directory is your world — back it up.

3

Pull the server image

Obtain the Windrose dedicated server image from the official source for your build. Pin to a specific version rather than tracking "latest" blindly, so you know exactly what you are running and can roll back if an update misbehaves.

4

Run it with the persistent directory mounted in

Start the container with your host data directory mounted at the path the image expects, and with the ports the server needs published to the host. Use a managed container definition (Compose file or an equivalent) rather than a one-off shell command, so the configuration is written down and repeatable.

5

Verify from the outside first

Before inviting anyone: confirm the container is running, confirm the server is listening on the expected ports, and confirm a player can connect from outside your own network. Only then start customising world settings.

Set a restart policy. Configure the container to restart automatically unless you explicitly stop it. A dedicated server that dies overnight and waits for you to notice is worse than no dedicated server, because everybody's plans depended on it.

If the container starts and then immediately exits, the two usual causes are a data directory it cannot write to and a port that is already taken. Check the container logs first — they are more informative than any guess.

WorldDescription.json — What It Controls

WorldDescription.json is the world description file for your dedicated server: the file that describes the world you are serving rather than the server process itself. It is where world-level settings live. If you have ever wanted a fresh world to start differently from the defaults, this is the file.

Edit it stopped, not running. Edit the world description file while the server is shut down, then start the server so it reads the file on startup. Editing a live file risks the server overwriting your changes on exit, or reading a half-written file. Stop, edit, verify, start.

How changes take effect is the part people get wrong, so be precise about the two different cases:

SituationDo changes apply?
Editing before the world has ever been generatedYes — the new world is created from the file.
Editing an already-generated worldOnly settings the server re-reads at startup. Generation-time settings are already baked into the save.
Editing while the server is runningNo reliable effect, and it risks being overwritten on shutdown.

That middle row is the source of most "I changed it and nothing happened" reports. A world that already exists has already committed a lot of its state; changing a generation-time setting afterwards will not retroactively reshape it. If a change genuinely requires regeneration, that means a new world — which means saying goodbye to the old one.

Always back up the world first. Copy the server's world data directory to somewhere safe before touching configuration. Save recovery on a dedicated server is a manual, path-level operation, not a button — our Save Backup & Data Recovery Guide covers the procedure.

Remember the historical note from section 2: editing this file on a dedicated server was not possible before 0.10.0.6. If your changes seem to be ignored, confirm your server build is at or past that patch before you blame your own syntax.

Linux Docker vs Windows Self-Host

FactorLinux + DockerWindows self-host
AvailabilityOnly since 0.10.0.7, as a Docker imageAvailable from earlier builds
Setup difficultyModerate — needs Docker familiaritySimpler for most players
Idle resource useLow; a headless box is cheap to leave onHigher; a desktop OS is running
UpdatesPull a new image, recreate the containerRun the updater, restart
Remote administrationShell access, standard toolingRemote desktop usually required
Best forAlways-on worlds, VPS hosting, tinkerersQuick setup on a spare Windows PC

The honest recommendation: if you already have a Windows machine that is going to be on anyway, self-hosting on it is the lower-friction path and completely fine. If you want an always-on world, or you are renting a VPS, Linux with Docker is the better fit — lower idle overhead, cleaner remote administration, and no desktop environment eating resources. The two blockers that once made Linux awkward are both resolved.

Whichever you choose, the day-to-day operating work is the same: admin commands, backups, and the occasional restart. Our Dedicated Server Admin Commands Guide covers that side, and our Server Setup Troubleshooting Guide is where to go when it will not come up.

Post-Deploy Checklist & Troubleshooting

Work this list top to bottom whenever something is wrong. Most dedicated-server problems are one of these five.

Container starts then exits immediately

Almost always permissions on the mounted data directory, or a port already in use. Check the container logs before changing anything else.

Nobody can see or join the server

Networking, not Docker. Confirm the ports are published on the host, forwarded on the router, allowed through the firewall, and reachable from outside your own network. See the two port guides linked in section 3.

World settings changes are ignored

Confirm the edit was made while the server was stopped, and confirm the server build is at or after 0.10.0.6. Also confirm the setting is one the server re-reads on an existing world rather than a generation-time setting.

Server lags once the group builds up

Entity and structure load, not connectivity. Consolidate bases, retire unused vessels, and review the entity-bloat diagnostics.

Players connect but desync or rubber-band

That is connectivity quality, and it is the one case where relay-style options are relevant. Our Force Relay Connection Guide and Connection Region Mismatch Fix cover it. Keep the distinction straight: relay fixes how packets travel, it does not reduce how much the server has to simulate.

Finally, make backups routine rather than heroic. A scheduled copy of the world directory to a second location costs nothing and turns the worst possible server day into an inconvenience.

FAQ

When did Windrose get Linux dedicated server support?

Linux support arrived in patch 0.10.0.7, in late June, and it is delivered as a Docker image rather than a standalone binary.

Can I edit WorldDescription.json on a dedicated server?

Yes, on builds from 0.10.0.6 onward. Before that patch, dedicated servers could not modify the world description configuration at all — that was the fix.

Do world description changes apply to an existing world?

Only for settings the server re-reads at startup. Settings that are applied during world generation are already baked into an existing save and will not retroactively change it.

Should I edit the file while the server is running?

No. Stop the server, edit the file, verify it is valid, then start the server so it reads the new values on startup.

Can I run the server without Docker on Linux?

Officially Linux support is delivered as a Docker image. Anything else is unsupported and will vary by build — check the official documentation for your version.

Where should the world save live?

In a host directory or volume mounted into the container, never inside the container filesystem. Containers are disposable; your world is not.

Which ports do I need to forward?

Forward the ports your server build actually uses and verify reachability from outside your network. Our port forwarding guides cover the dedicated-server and co-op client sides separately.

Is a VPS better than hosting at home?

A VPS gives a stable address and someone else's uptime, which usually wins for a group spread across regions. A home box is free and fine for a small local group with decent upload.

Why does my container exit right after starting?

Most often the mounted data directory is not writable by the container's user, or a required port is already in use. The container logs will tell you which.

Does a dedicated server improve my own frame rate?

Yes, if you were previously the host. The world simulation moves off your gaming PC, so you become an ordinary client like everyone else.
