1. What the Click Offset Bug Looks Like on macOS

The RuneLite click offset bug on macOS is one of the most confusing client problems a player can run into, because nothing about your mouse or trackpad is actually broken. What happens is that the spot where RuneLite registers the click is in a different place from where your cursor visually points. You click on a bank booth, but the game acts as if you clicked an empty tile three spaces to the right. You try to equip an item from your inventory, but the wrong slot gets activated. You attempt to move to a safe tile during a boss fight, and your character walks the wrong direction instead. To the eye, your cursor is perfectly accurate; to the game engine, the input coordinate has been translated by a consistent offset, usually diagonally.

This mismatch is almost always proportional to your display scaling ratio. On a Retina MacBook Pro running at the "More Space" setting, the offset can be large enough that the top-left of the game canvas maps to a click that lands far down and to the right of where you intended. On a non-Retina external monitor at 1.0 scaling the bug often disappears entirely, which is why many players only notice it after docking their laptop or after plugging in a high-resolution external display. The inconsistency between monitors is itself a strong clue that the problem is scaling-related rather than hardware-related.

🎯 Common Symptoms Checklist

  • Clicks register offset diagonally (most common: down-right) from the cursor.
  • The offset grows larger as you increase macOS "Display scaling" toward "More Space".
  • Bank pins, inventory slots, and chat-box buttons respond in the wrong place.
  • Right-click menus appear over the wrong tile or NPC.
  • Switching from a Retina laptop screen to a 1080p external monitor fixes it temporarily.
  • Restarting RuneLite sometimes fixes it for one session, then it returns after a reboot.

It is important to understand that this is not the same as general input lag, nor is it a problem with your trackpad drivers, nor is it caused by a specific RuneLite plugin. Disabling plugins does not fix it. Lowering your mouse sensitivity does not fix it. The only thing that reliably changes the offset is changing how macOS and RuneLite agree on pixel coordinates. That is why the rest of this guide focuses entirely on scaling, resolution, and the Java runtime, the three layers that actually control coordinate mapping on macOS.

💡 Quick Diagnostic Test

Open the RuneLite Settings panel and enable the "Client" → "Show Mouse Crosshair" option if available, or simply try clicking the exact center of a known interface button like the "Log Out" button while watching where the highlight appears. If the highlight lands away from your cursor, you have a confirmed offset and should follow Section 5's step-by-step fix.

Players sometimes confuse the offset bug with a completely different issue: a stuck or ghost click caused by the "Mouse hover" plugin misreading coordinates. If your clicks are random rather than consistently offset, that is a different problem. The offset described here is consistent and proportional, which is the signature of a scaling mismatch. Keep this distinction in mind, because the fix for a random-click bug (usually a bad plugin or a corrupted config) is different from the scaling fix below.

2. The HiDPI / Retina Scaling Root Cause

To understand why the click offset happens, you need a basic mental model of how macOS handles high-density displays. A Retina screen has a very high physical pixel count, but macOS does not expose those physical pixels directly to applications. Instead, it works in "logical" points. On a Retina display, one logical point is usually backed by two physical pixels in each direction (a 2.0 backing scale), or by a fractional scale such as 1.5 or 1.25 when you pick a "Scaled" resolution in System Settings. The benefit is that text and UI stay a comfortable size while the screen stays sharp. The cost is that every application must translate between logical coordinates (where your cursor is) and physical coordinates (where pixels are actually drawn).

RuneLite is a Java application built on the AWT/Swing toolkit, and historically Java's handling of macOS HiDPI rendering has been fragile. When Java reports one scaling factor to the operating system but RuneLite's input handling computes click positions using a different factor, the game receives a click location that is multiplied or divided incorrectly. Concretely: macOS tells the OSRS client that the canvas is, say, 1280 logical points wide. RuneLite draws the game at 1280 logical points but, because of a Java backing-scale mismatch, the input subsystem maps a cursor at logical point 640 to physical pixel 960 instead of 1280 (or vice versa). The result is a click that is shifted by the ratio between the two scale factors. Because the ratio is constant across the whole window, the offset is uniform and proportional, which is exactly the pattern players observe.

🎯 Why Retina Triggers It and Non-Retina Does Not

  • Retina displays use a backing scale of 1.25, 1.5, or 2.0, forcing a coordinate translation.
  • Standard 1080p monitors use 1.0 scale, so logical and physical pixels match and no translation error occurs.
  • Java's older AWT pipeline assumed 1.0 scale on many code paths, so any non-1.0 scale exposes the bug.
  • "More Space" scaling on macOS uses fractional ratios that are the hardest for Java to handle correctly.

The key historical detail is that this class of bug existed in the underlying Java runtime for years. Older builds of the JDK computed the device scale factor inconsistently between the rendering path and the event-dispatch path. When RuneLite was launched through a wrapper that did not pass the correct HiDPI flags, the canvas would render at one scale while mouse events were delivered at another. Jagex's official client behaves differently because it uses a different Java packaging and its own input layer, which is why many macOS players report the offset only in RuneLite and not in the official client. That contrast is useful confirmation that the root cause is the RuneLite-plus-Java-plus-macOS interaction, not the game servers.

There is a second, related mechanism worth knowing about: the macOS "Displays have separate Spaces" and "Automatically rearrange Spaces" options. When you drag the RuneLite window from a Retina laptop screen to a non-Retina external display, macOS changes the backing scale of the window on the fly. If Java caches the old scale factor instead of re-querying it, every subsequent click is computed with the stale factor until you restart the client. This explains the very common report that "the offset only appears after I move the window to my second monitor." The fix is twofold: keep displays at a matched scale when possible, and restart RuneLite after any monitor change so Java re-reads the correct factor.

💡 Fractional vs Integer Scaling

If you must use scaling, prefer an integer ratio (such as the default "Default" Retina setting, which is a clean 2.0 backing scale) over a fractional "Scaled" setting like "More Space." Integer scales are far less likely to trigger the Java mismatch because the math stays whole-number and both rendering and input agree on it.

Finally, note that the GPU plugin and other rendering plugins can worsen the perceived problem. When the GPU plugin renders the game through a custom OpenGL surface, it sometimes compounds the scale mismatch because the plugin's framebuffer is sized in physical pixels while the input handler still works in logical points. If you have the GPU plugin enabled and still see an offset after applying the core fix, you may want to read our companion article on GPU performance, because tuning the renderer can interact with the scaling fix. We cover that alongside the offset repair in the next steps, and you can also consult our dedicated RuneLite GPU FPS drop fix guide for the rendering-side details.

3. Resolution & Client Scaling Fixes

With the root cause clear, the practical fix is to make macOS and RuneLite agree on a single scale factor. There are three places where scale is decided: the macOS display setting, the RuneLite "Display scaling" option, and the game client's "Resizable" mode. Getting all three aligned is what eliminates the offset.

3.1 Match macOS Display Scaling

Open System Settings → Displays on your Mac. You will see a row of scaling options. The safest choice for RuneLite is the "Default" option for a Retina laptop (which uses a clean 2.0 backing scale) or, for an external monitor, the setting that yields a 1.0 backing scale. Avoid "More Space," which forces a fractional scale that Java struggles with. If you need more screen real estate, prefer reducing the RuneLite window size rather than pushing macOS into a fractional scale.

3.2 Use RuneLite's Stretched Mode Carefully

RuneLite has a "Stretched Mode" plugin that scales the fixed 765x503 game canvas up to fill a larger window. Stretched Mode is a frequent offender for click offset because it introduces its own scaling layer on top of macOS scaling. The plugin maintains a "Scaling factor" and a "Scaling type" (nearest-neighbor versus bilinear). If the stretched canvas scale does not match the OS scale, clicks drift. The reliable approach is to either disable Stretched Mode entirely and play in normal Resizable mode, or to set the stretched scaling so that one game pixel maps cleanly to an integer number of device pixels.

🎯 Stretched Mode Safe Settings

  • If you keep Stretched Mode on, set "Scaling type" to "Nearest-neighbor" for predictable mapping.
  • Keep the "Maximum scaling" within an integer multiple of your OS backing scale.
  • Disable "Scaling on keypress" so the scale does not change mid-session.
  • Disable "Integer scaling" only if you have verified clean offset-free clicks without it.

3.3 Prefer Resizable (not Fixed) or Vice Versa Consistently

Some players fix the offset simply by switching between "Fixed" and "Resizable" client modes, because each mode computes its canvas origin differently. In Resizable mode the game canvas can be dragged, and its top-left origin shifts; if a stale origin is cached, clicks offset. Toggling the mode forces RuneLite to recompute the canvas rectangle and often clears a cached bad offset. This is a fast first attempt before deeper changes.

3.4 Watch External Monitors

If you play on an external display, set that display's scaling to match the laptop's backing scale as closely as possible, or accept 1.0 on the external and keep RuneLite on the external only. Mixed-DPI across two screens is the single most common cause of recurring offset. When in doubt, play fullscreen on a single display and close the laptop lid or mirror rather than extend.

💡 Test After Every Change

After changing any scale setting, restart RuneLite completely (quit from the menu bar, do not just close the window) and re-run the diagnostic click test from Section 1. Java only re-reads the scale factor at launch, so a mere settings change without a restart will not fix the offset.

Players coming from our combat content will recognize that a misaligned click during a dangerous fight can be fatal. If you are training at aggressive monsters or learning bosses while fighting this bug, consider pausing PvM until the offset is gone. 4. Java & macOS Version Requirements

Because the bug lives in the Java runtime's HiDPI handling, the version of Java that launches RuneLite matters as much as your display settings. RuneLite ships with its own bundled JRE on most platforms, but on macOS the exact build determines whether the scaling fix is even possible.

4.1 Use a Modern, HiDPI-Aware Java

Java 8 was where most of the original macOS Retina click-offset bugs lived, because early Java 8 builds had no proper backing-scale support in AWT. Java 11 and later (especially Java 17 and Java 21) corrected most of the coordinate translation logic, but only if RuneLite is actually launched with that runtime. Modern RuneLite releases bundle a current JRE, so the first step is to make sure you are on the latest RuneLite version, which pulls in a current Java. If you launched RuneLite through a manually installed JDK or through a third-party launcher, you may be on an old Java that reintroduces the bug.

🎯 Java Checklist

  • Update RuneLite to the newest release so the bundled JRE is current.
  • If using a system JDK, use Java 17 or 21, never Java 8 for macOS HiDPI.
  • Remove stale JAVA_HOME pointing at an old JDK if you launch from terminal.
  • Let RuneLite manage its own Java; avoid forcing a custom runtime unless necessary.

4.2 macOS Version Considerations

Apple changed how display scale and "Displays have separate Spaces" behave across macOS releases. On macOS Sonoma and Sequoia the window-server handles per-display scale more aggressively, which can re-trigger offset after monitor changes. On older macOS versions the behavior was more stable but the underlying Java bug was worse. The practical advice is to stay on a current macOS that RuneLite's bundled Java supports, keep RuneLite updated, and avoid dragging the client between displays mid-session.

4.3 Launch Flags That Help

Advanced users can pass JVM flags that force correct HiDPI handling. The most relevant is enabling the modern AWT HiDPI pipeline. In current Java this is usually automatic, but if you must, launching with the flag that enables the unified HiDPI scale reporting can help. However, editing launch flags risks breaking the client, so only do this if the simpler scale-matching steps in Section 3 failed. Most players never need flags once RuneLite and Java are current and the display scale is matched.

💡 Check Your Active Java

You can confirm which Java RuneLite is using by opening the RuneLite log file (found in your RuneLite settings folder) and looking for the "Java version" line at startup. If it says Java 1.8 (Java 8), that is almost certainly your problem and you should reinstall the current RuneLite build.

Keeping Java current is also a security matter. Old Java runtimes have known vulnerabilities, and since RuneLite runs with access to your account session, an outdated runtime is a risk beyond just click offset. Treat a Java update as part of normal client hygiene, the same way you would keep your OS patched.

5. Step-by-Step Fix Walkthrough

This is the ordered procedure that resolves the macOS click offset in the large majority of cases. Follow it in sequence and test after each major step rather than applying everything at once, so you know which change worked.

Step 1 — Confirm the Offset

Run the diagnostic from Section 1. Click a known interface element and observe whether the highlight lands away from your cursor. If there is no offset, you do not have this bug and should look at plugin conflicts instead.

Step 2 — Quit RuneLite Fully

Right-click the RuneLite icon in the macOS menu bar and choose Quit, or press Cmd+Q. Do not just close the game window; the Java process must exit so it re-reads scale factors at next launch.

Step 3 — Set macOS Display Scaling

Open System Settings → Displays. On a Retina MacBook choose "Default." On an external monitor choose the 1.0 (largest text is not needed; pick the native resolution) option. Avoid "More Space." If you use two displays, set them to the same backing scale or play on one display only.

Step 4 — Update RuneLite and Java

Launch the RuneLite installer/app and let it update. Confirm the bundled Java is version 11 or newer via the startup log. If you previously forced a custom JDK, remove that override.

Step 5 — Disable or Reconfigure Stretched Mode

Open RuneLite → Configuration → Stretched Mode. Either untick "Enabled," or keep it on but set "Scaling type" to "Nearest-neighbor" and ensure the scaling factor is an integer multiple of your OS backing scale. Restart RuneLite again.

Step 6 — Toggle Client Mode

In-game, open the Settings cog and switch between "Resizable" and "Fixed" once, then settle on the mode you prefer. This recomputes the canvas origin and clears any cached bad offset.

Step 7 — Re-Test

Repeat the Section 1 diagnostic. Clicks should now register exactly under the cursor. If a small residual offset remains, nudge the macOS scaling one notch toward "Default" and restart once more.

🎯 If It Still Fails

  • Delete the RuneLite settings file and reconfigure from scratch (back up first).
  • Try the official Jagex launcher as a control test to confirm it is RuneLite-specific.
  • Play fullscreen on a single non-Retina external monitor at 1.0 as a last resort.
  • Report the exact macOS version, Java version, and display model to the RuneLite GitHub issues.
💡 Backup Before Resetting

Before deleting any RuneLite config, export or copy your settings folder. You can lose plugin layouts and hotkeys. A settings reset is powerful but should be a deliberate last step, not your first move.

Most players resolve the offset at Step 3 or Step 5. The combination of a matched macOS scale and either disabled Stretched Mode or clean integer stretched scaling accounts for the overwhelming majority of fixes. Java updates (Step 4) handle the remaining cases where the runtime itself was the culprit.

6. Preventing the Offset From Coming Back

Once fixed, the goal is to keep it fixed. The offset returns most often after a macOS update, after plugging in a new monitor, or after toggling scaling for a presentation. A few habits keep you safe.

6.1 Lock Your Display Configuration

Pick one scaling setting and keep it. If you need "More Space" for productivity work, consider playing RuneLite on a separate non-Retina monitor at 1.0, or accept that you may need to restart RuneLite after switching scale modes. The fewer scale changes your Mac makes, the fewer chances Java caches a stale factor.

6.2 Restart RuneLite After Monitor Changes

Any time you dock, undock, or move the window between displays, quit and relaunch RuneLite. This forces Java to re-query the current backing scale. It takes ten seconds and prevents the most common recurrence.

6.3 Keep Auto-Update On

RuneLite ships fixes for macOS input handling in regular updates. Leaving auto-update enabled means you pick up HiDPI corrections as soon as they are released. Disabling updates to "stay stable" often backfires on macOS because you miss the exact patches that fix offset bugs.

6.4 Avoid Conflicting Launchers

Do not run RuneLite through multiple launchers or wrappers that each bundle a different Java. Pick the official RuneLite macOS app as your single source of truth. Mixed runtimes are a quiet source of recurring offset.

💡 Make It a Routine

Treat "relaunch RuneLite after any display change" as a reflex, the same way you would save your work before a reboot. It is the single cheapest insurance against the offset ever returning.

With these habits, the click offset becomes a one-time fix rather than a recurring frustration. The underlying macOS and Java behavior does not change on its own; it only bites when scale factors diverge, and you now control every factor that can diverge.

7. macOS Click Offset FAQs

Why do my clicks land to the bottom-right of where I point?

That diagonal shift is the classic signature of a scaling mismatch. macOS renders the game canvas at a logical scale while RuneLite's input handler uses a different scale factor, so every click coordinate is multiplied incorrectly and pushed down and to the right. Matching your macOS display scale to RuneLite's scaling (Section 3) and updating Java (Section 4) resolves it.

Does this bug happen on Windows or Linux too?

It is overwhelmingly a macOS problem because of how Apple's window server handles Retina backing scales and how Java's AWT toolkit historically translated them. Windows and Linux use different scaling models, and while a similar offset can appear with mismatched DPI there, the macOS Retina case is by far the most reported. The fix philosophy is the same: align the OS scale with the client scale.

Will disabling Stretched Mode lower my visual quality?

Stretched Mode upscales the fixed 765x503 canvas to fill a larger window, which can look softer. Disabling it means playing at the native canvas size or in Resizable mode, which is sharper and removes the extra scaling layer that causes offset. If you want a larger view, use Resizable mode rather than stretched scaling; it avoids the click-drift entirely.

My offset only appears when I plug in an external monitor. Why?

You are running a mixed-DPI setup: a Retina laptop at 2.0 backing scale and an external monitor at 1.0. When you move RuneLite between them, Java can cache the old scale factor and compute clicks with the stale value until you restart. The fix is to relaunch RuneLite after any monitor change and, ideally, keep both displays at a matched scale or play on a single display.

Should I use the official Jagex client instead of RuneLite on Mac?

The official client uses a different Java packaging and input layer, so some players find it avoids the offset. However, you lose RuneLite's plugins. Most players prefer to keep RuneLite and apply the scaling fix in this guide, which restores accurate clicks while keeping all the quality-of-life features. Use the official client only as a diagnostic control if the offset persists.

Updating RuneLite did not fix it. What now?

If the offset remains after updating and matching scales, the cached config may be corrupt. Back up and delete your RuneLite settings file, then reconfigure from scratch. Also verify the bundled Java is version 11 or newer via the startup log. As a final test, play fullscreen on a single non-Retina monitor at 1.0 scale to confirm the input layer itself is healthy.
